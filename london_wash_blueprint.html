SHEET 06

Monetary architecture new

Data

You're right to push on this — Rev 1.0 specified numeric(12,2), which avoids floating-point error but doesn't by itself stop rounding drift once amounts pass through GST splits, percentage promos, loyalty-point conversion, subscription proration, and split payments. Each of those is a division or percentage operation, and if every module rounds its own fractional paise independently, a wallet ledger and an order ledger can each be individually correct and still disagree by a few paise in total. The fix isn't a bigger decimal column — it's making every rounding decision happen in exactly one place.

ADR-10 · Money representationdecision
Alternatives
(a) NUMERIC(12,2) fixed-point decimal, as originally specified. (b) Integer minor units (paise for INR, cents generally) stored as bigint. (c) An arbitrary-precision decimal string type.
Trade-offs
NUMERIC is readable directly in SQL and fine for simple single-currency ledgers, but GST %, promo %, loyalty conversion, and split-payment remainders all still produce fractional paise that someone has to round — and "someone" tends to mean several call sites, each doing it slightly differently over a codebase's lifetime. Integer minor units make every amount an exact integer with no fractional representation possible at all: sums, comparisons, and equality checks are trivially correct, and the only place a rounding decision can occur is the single shared Money utility that converts a computed fraction (18% of ₹450) down to a whole number of paise. This is the same pattern Stripe and Razorpay use internally. The one cost is that every display layer must divide by 100 (or the currency's minor-unit exponent) at the UI boundary — a one-line formatter, applied once.
Recommendation
Integer minor units. Every monetary column becomes bigint storing the amount in paise, paired with a currency char(3) column (ISO 4217) even though V1 is INR-only. A single shared Money value object ({amountMinor: bigint, currency: string}) is the only code in the entire system permitted to perform arithmetic on money — no controller, no report query, no AI tool function computes a percentage of an amount by hand.

Where rounding decisions are made explicit

OperationRounding rule
GST calculation (when enabled, §19)round-half-up to the nearest paise, applied once to the tax-inclusive line total, never per-item then summed
Percentage promo / discountround-half-up; discount is capped so it can never exceed the line subtotal
Loyalty point ↔ currency conversionpoints always redeem to whole paise; any fractional remainder stays as unredeemed points rather than being paid out
Split payment across N methodsfirst N−1 splits are floor-rounded; the final split absorbs whatever paise remain, so the sum always equals the total exactly — a documented, deterministic rule rather than an ad hoc "closest split gets the remainder"
Subscription prorationpieces/credits consumed round down (customer-favourable) to avoid ever over-charging a subscription balance

This also changes the entity specs in §08 — every numeric(12,2) from Rev 1.0's Payment/Order/Wallet tables is now bigint minor units.

SHEET 11

RBAC architecture

Platform services

Unchanged in structure — permission-based, roles scoped to a branch or the organization. One addition: approval authority is itself a permission, not a side-effect of a role name.

PermissionMeaning
approvals:decide:refundmay approve/reject a pending refund request
approvals:decide:price_overridemay approve/reject a pending price-override request
approvals:decide:payroll_adjustmenttypically Owner/Accountant only — deliberately separate from the Branch Manager's other approval permissions

This matters because "Branch Manager approves everything" is exactly the kind of blanket rule that defeats the point of dual control — a manager who can both request and approve the same action type has approved nothing. The guard checks requested_by !== decided_by unconditionally, on every action type, regardless of role.

ADR-11 · Single-approver vs. multi-level sign-offdecision
Trade-offs
A single required approver is enough friction to stop most misuse and mistakes without slowing the counter down. Multi-level (e.g. Manager, then Owner, for very large refunds) adds real safety for the rare large-amount case but meaningfully slows every other approval if built as one rigid chain.
Recommendation
Ship single-approver in V1 — the approval_rule.approver_roles column is already an array and the request/decision model already supports a decision sequence, so adding a second required step later (e.g. only above a much higher amount) is a configuration change, not a schema migration.

A request that sits unactioned past escalate_after_minutes is picked up by the Automation Engine (§22) — "WHEN approval pending > N minutes THEN notify the next role up" — reusing the mechanism already built for SLA alerts rather than inventing a parallel escalation system.

SHEET 19

Tax & GST engine new

Compliance

Built for Kerala, India from the start, switched off until you're ready — exactly as you asked. Invoicing without GST today and turning it on later is a settings change, not a migration, because the tax calculation was never hard-coded out of the pricing flow; it's a step that's simply skipped while the toggle is off.

Enable GST calculation
Settings → Finance → Tax  ·  OFF at launch — orders total without a tax line until you switch this on

What's configured, ready to switch on

ItemValue researched for Kerala laundry/dry-cleaning
SAC code999712 — dry-cleaning services (covers wash & fold / wash & iron / dry-clean under the same heading)

Intra-state split (Kerala customer, Kerala branch)CGST 9% + SGST 9%

GST rates move by Council notification — this is exactly why §06/§07 store TaxRule as a dated, versioned record rather than a constant: when the rate next changes, you add a new rule with a new effective_from date, and every invoice already issued keeps the rate it actually charged.

ADR-12 · Tax engine defaults to offdecision
Why it matters
Whether to charge and register for GST is a business/accounting decision tied to your turnover and registration status, not something the software should decide by shipping tax-on by default.
Recommendation
A single org-level SystemSetting (tax.enabled, boolean, default false). While off, Order totals skip the tax step entirely — no GST line, no CGST/SGST split — and the invoice template omits GSTIN and tax fields rather than printing zeros. When you're ready, an admin enters the branch GSTIN and flips the toggle; nothing else in the order/pricing flow changes.

One limit worth stating plainly: this toggle controls what the software computes and prints. Whether and when London Wash is legally required to register for and charge GST is a determination for you and your accountant, not something this document or the AI copilot (§21) can decide — consistent with the boundary your original brief draws around AI and legal/financial authority.

SHEET 20

Privacy & consent module new

Compliance

You're right that this was missing as its own area — CRM (§04) had customer preferences, but nothing owned consent as a legal record, or gave a customer a way to export or delete their data. This module fixes that, and the timing matters: India's Digital Personal Data Protection Act rules were notified on 13 Nov 2025, with consent, notice, and security obligations becoming fully enforceable on 13 May 2027 under the Data Protection Board of India. That's inside this programme's build window — worth having in place well before it's mandatory, not scrambled together against the deadline.

Deletion means anonymisation, not erasure — and here's why

A customer's order history is also your financial ledger (§05/§18's immutability rule, and likely statutory bookkeeping retention requirements). Hard-deleting a customer would either break every historical order/payment/garment-event row that references them, or force deleting financial records outright — neither is acceptable. The resolution: on an approved deletion request, personally identifying fields (name, phone, address, stored photos) are overwritten on the Customer row and linked CustomerAddress/GarmentPhoto rows; the order, payment, and garment-event history remains, now attached to an anonymised customer stub instead of an identifiable person. This satisfies an erasure request without corrupting your books.

Like refunds and payroll (§12), a deletion request is itself routed through the approval workflow — it's irreversible, so it gets a human check, not an instant self-service button.

ADR-13 · Where consent is enforceddecision
Alternatives
(a) Check consent at each UI/portal entry point. (b) Enforce centrally inside the Notification dispatch service. (c) Enforce via a database-level access policy.
Trade-offs
Checking at the UI is the easiest to forget — a new "send a promo blast" feature added six months from now could bypass it entirely if the check isn't structural. Enforcing at the database layer is robust but awkward for something that's really a business rule about message dispatch, not row visibility.
Recommendation
Enforce inside the Notification dispatch service (§16) — every channel adapter already funnels through this one chokepoint (§14 in Rev 1.0's brief), so the consent check happens exactly once, for every notification, regardless of which module triggered it.

Note on scope: transactional/service messages (order ready, pickup confirmed) are treated separately from marketing sends under most consent frameworks, including the practical shape of India's Act — but the precise line between "service" and "marketing" for your specific message templates is worth a short review with counsel before go-live, not something this document finalises unilaterally.

SHEET 35

Pricing engine & price lists new

Commerce

You caught a real gap. Rev 1.0/1.1 modelled pricing as a single flat PriceRule table — one price per (item, service), full stop. That's wrong for a business that serves both walk-in retail customers and contracted hotel/corporate accounts at different rates for the same garment: a hotel's bulk bedsheet rate and a walk-in customer's per-piece rate are not the same number, and a single table can't hold two different "correct" prices for "Bedsheet / Wash & Fold" at once. The working UI model you're reviewing had the same flaw — one flat catalogue — until this addendum.

ADR-14 · Multi-tier pricing modeldecision
Alternatives
(a) One flat catalogue with a per-customer discount percentage applied at checkout. (b) One flat catalogue with per-corporate-account override rows layered on top. (c) Fully independent named price lists — a customer is assigned one profile, and every item/service is priced separately per profile.
Trade-offs
A flat catalogue + discount % (a) is simplest to build but can't express a hotel rate that's cheaper on some items and more expensive on others than retail (common in real bulk-linen contracts — high volume on basic items, premium handling on delicates) — a single percentage can't capture that shape. Override rows on top of a base catalogue (b) gets closer, but every report and every POS lookup now has to ask "is there an override for this customer on this item? if not, fall back to base" — two lookups, two sources of truth, and a class of bug where the fallback logic itself has an edge case. Fully independent named profiles (c) cost one extra table and one extra join, but every price lookup becomes a single, unambiguous query: "this customer's profile id, this item, this service, current row" — no fallback branching, no two sources of truth, and no ambiguity from matching on item+service text instead of a stable row id.
Recommendation
Independent named price list profiles (c). PriceListProfile (§08) holds named, reusable lists — "Standard Retail," "Corporate / Hotel," or a dedicated list per large account like "Corporate — Grand Heritage Hotel." Each Customer carries a price_list_profile_id; every order prices its lines by looking up that customer's profile against PriceListEntry rows, keyed by entry id, never by matching item+service strings. One branch-wide default profile catches customers with no explicit assignment. This is the pattern now live in the working UI console's new Services & Price Lists screen (Catalogue nav group).

How a price is resolved

StepWhat happens
1POS/portal reads the customer's price_list_profile_id (falls back to the branch's default profile if unset)
2Catalogue chips shown are filtered to PriceListEntry rows for that one profile — a hotel account never sees, or accidentally selects, a retail-priced row
3Each order line stores the price_list_entry_id it was added from, plus a snapshot of the price paid — a later price change never rewrites a past invoice, same discipline as tax_rule in §19
4Promotions/coupons (existing catalogue module) apply on top of the resolved line price, unchanged from Rev 1.1

Managing price lists (admin)

The Services & Price Lists screen (Catalogue nav group in the admin console) has two views: Services & Pricing — the priced items within one selected profile, with add / activate-deactivate / remove actions — and Price List Profiles — the list of named profiles themselves, each showing how many items are priced and how many customers are assigned, with a "+ Add price list" action for creating a new one (e.g. a dedicated contract rate card for a new hotel account). A customer's assigned profile is set from their customer record and immediately changes which catalogue they see in POS/New Order.

This also updates §04 (catalogue module now owns price_list_profile/price_list_entry instead of the old flat price rules), §07 (ERD), and §08 (two new entity cards) from Rev 1.1. Phase 2's DDL deliverable (§30) now includes these two tables.
